# A 6502 gem4xe, and what the toolchain will and will not do for it

Status: **step 1 done 2026-11-14** (branch `6502`): the VDI and its ANTIC
device, banked in five PORTB banks, draw on a stock 6502 and match the
model pixel for pixel (`make test-v6`).  See "Step 1" below. This records what was measured, so the
design argument rests on the toolchain's actual behaviour rather than on a
sentence in its manual.

Reproduce everything here with `python3 tools/bsp6502/probe.py`.

## The question

gem4xe needs a 65C816 today. A 6502 build would need banked code, and
Calypsi's 6502 linker has a banking mechanism (`scatter-to`,
`:generate-instances`, a `bankedcode` section) whose documentation says:

> Somewhat simplified, once properly linked, the compiler runtime handles
> the bank system automatically.

Read one way that promises a trampoline on every cross-bank call, which
would make a 6502 port mostly a matter of writing a linker map. Read
another way it promises only that the *relocation arithmetic* is handled.
The difference decides the whole architecture, and no documentation in the
toolchain settles it — there is no worked example of a banked **call**
anywhere in `doc/`, only of banked placement.

So it was asked of the toolchain directly: a resident `main()` in bank
`$00` calling two functions placed in `bankedcode`, linked against a
throwaway Atari map with the PORTB window at `$4000-$7FFF`.

## What came back

**1. A call into banked code is a plain `jsr`.**

```
main:   ...
        jsr  $4260        ; far_a, at its address INSIDE THE SLOT
        jsr  $4000        ; far_b
```

No bank switch, no veneer, no runtime call. The program is responsible for
having the right bank mapped before the `jsr`.

**2. That is not a shortcoming of an unsupported target.** The same two
object files linked against Calypsi's *own* `cx16-banked.scm` — a target it
supports — produce `jsr $A260` / `jsr $A000`: the identical plain call at
the X16's slot address.

**2a. But a banked-call runtime DOES exist — it just cannot be reached
from C.** `src/lib/lowlevel/mega65CodeSlot5.s` ships `_JmpInline24` (a
banked call with the 24-bit destination embedded after the `jsr`) and
`_JmpInd24` (the same through `_Zp[8-10]`, "intended for function pointer
calls"), with `.rtmodel codeSlot,"5"`; `src/lib/lowlevel/bank.h` has the
`jumpInd`/`restore` macro pair that pushes the old bank, switches, jumps
indirect and restores on return. Both are guarded by
`__CALYPSI_TARGET_SYSTEM_MEGA65__` / `__CALYPSI_TARGET_SYSTEM_FOENIX__`.

So the design exists and is somebody's finished work. What could not be
found is anything that *selects* it: the compiler emits
`.rtmodel codeModel,"plain"` and a bare `jsr` on every target that can be
driven here — including `--target MEGA65 --core 45gs02` — there is no
`--code-model` option on `cc6502`, `--rtattr codeModel=banked` is ignored,
no header declares a banked keyword or attribute, and `mega65-banked.scm`
turns out to bank *data* (`(type data) (qualifier far)`) with no
`bankedcode` section at all. **So the honest statement is: banking is
placement only as far as anything reachable from C goes, and the question
for upstream is how the code model is selected, not whether it exists.**

**3. Two functions in different banks can share one runtime address, and
nothing says so.** With the slot small enough to force several instances,
`far_b` and `t100` both resolve to `$4000`, and `t112` and `t183` both to
`$45E8`. The linker exits 0 and emits no diagnostic; `ln6502` has no
warning, check, or bank-related option at all. In the linked image a
`jsr $4000` is genuinely ambiguous — which function it reaches depends
entirely on what is mapped at the moment it executes.

## What that means for the port

**gem4xe would own the bank register, the way GEOS owns it.** That is a
known-good design, not a blocker. But the third finding is the one to build
around, because it is this project's recurring failure shape: **a wrong
cross-bank call compiles, links silently, and jumps to whatever happens to
be mapped.** It is not a diagnosable error; it is a wrong answer delivered
confidently.

Three consequences follow.

**Everything mutually callable must share a bank, or go through a
resident trampoline.** 16 KB per bank against roughly 216 KB of code (the
current 146 KB of far code times the measured 1.48× the 6502 costs) means
about fourteen banks, so partitioning alone cannot carry it. Cross-bank
calls need a bank-saving trampoline in bank `$00`.

**A post-link gate has to be written, because the toolchain has none.**
The information exists: each bank instance's contents are stored at a
unique address in the scatter destination, so a function's bank is
derivable from the instance layout even though the symbol table does not
record it. A checker can then require that every `jsr`/`jmp` whose target
lies in a different bank from its caller goes through a registered
trampoline. That is a `tools/ccbug/mscan.py`-shaped job, and it is ours to
build — see `make-a-silent-check-fail-first`: it needs a fixture that must
report, or its silence means nothing.

**GEM's 1984 ABI is unusually kind here.** The VDI and AES pass arguments
through fixed global arrays (`contrl`, `intin`, `ptsin`, `intout`,
`ptsout`), and `src/sys/abi.s` already implements the copy-in/copy-out
discipline that goes with them. Put those arrays in resident bank `$00` and
a banked caller and a banked callee never dereference a pointer into
memory that is switched out. The calls that *do* carry pointers —
`objc_draw(tree)`, `rsrc_load`, `form_alert`, `v_gtext`, an MFDB's
`fd_addr` — are exactly the ones the 65C816 build already bounces through a
near buffer for a different reason (`abi-near-of-far-string-bug`), so the
machinery has a precedent in the tree.

## What the machine would be

Encouragingly, not an exotic one:

| | |
|---|---|
| CPU | stock 6502 — **no accelerator** |
| RAM | ≥1 MB: a PORTB expansion, or an Axlon (to 4 MB, at $CFFF) -- found at load, the larger taken (a 130XE's four banks cannot hold ~216 KB) |
| Video | **no VBXE needed** — the ANTIC driver already ships; a VBXE, which works on a stock 6502 too, is supported as on the 65C816 (step 6) |
| Storage | SpartaDOS X / APT / CF, all already gated |

The display is genuinely solved rather than promised: `test-m26` boots the
shipped `GEM.COM` on a VBXE machine, on one without, and with
`VIDEO=ANTIC` overriding a working VBXE, with nothing typed in any of the
three. Without a VBXE it runs 320×192 in two colours with Atari's
condensed 6×6 face — **53×32 cells**, which is a usable desktop rather than
a token one.

## The map the BSP would have to define

```
$2100-$373F  LoRAM: zdata/stack/data   5,696 B   keep (95.5% full today)
$3740-$3FFD  Near: resident code       2,238 B   keep (84.9% full today)

$A000-$BFFF  unused                    8,192 B   NOT OURS -- SpartaDOS X

```

### How the window is actually switched

From *Mapping the Atari*, Revised Edition (Chadwick, 1985) — Appendix 12 for
the register and Appendix 16 for the 130XE bank modes — cross-checked against
Altirra's `mmu.cpp`:

**One register, `PORTB` at `$D301`.** On the 400/800 this was an input port
driving joystick ports 3 and 4; the XL/XE dropped those ports and repurposed
it for memory management, so it reads back what was written and a bank switch
is a read-modify-write of one byte.

| bit | meaning |
|---|---|
| 0 | OS ROM at `$C000-$CFFF` and `$D800-$FFFF`; **0 = RAM** |
| 1 | BASIC: **0 = enabled**, 1 = disabled (`$A000-$BFFF` becomes RAM) |
| 2, 3 | 130XE bank select (1200XL: LEDs) |
| 4 | **CPU** Bank Enable, active low |
| 5 | **Video** (ANTIC) Bank Enable, active low |
| 6 | reserved on XL/65XE |
| 7 | self-test ROM at `$5000-$57FF`; normally 1 |

**The CPU's and ANTIC's views are enabled separately**, which gives the four
modes Appendix 16 names: compatibility, CPU-extended, video-extended and
general. ANTIC can therefore look at a different bank from the one the CPU
executes from — irrelevant to banked code, but it means the window is not
purely a code slot, and on a VBXE-less machine the ANTIC framebuffer must not
be put behind it.

**Which bits are bank-select depends on the board**, and larger expansions
steal bits 1 and 7 — which is why BASIC and self-test cannot be enabled at
all on a 1 MB machine:

| RAM | extra 16K banks | bank bits |
|---|---|---|
| 128K (130XE) | 4 | 2, 3 |
| 192K | 8 | 2, 3, 6 |
| 256K / 320K | 12 / 16 | 2, 3, 5, 6 |
| 576K | 32 | 1, 2, 3, 5, 6 |
| **1088K** | **64** | **1, 2, 3, 5, 6, 7** |

Polarity is not uniform either: the enable bits are active-low, a 130XE's
bank bits hold the bank number directly, and the boards that add lines differ
among themselves — some orderings exist so that particular values alias main
RAM. **So a bank number cannot be turned into a PORTB value by a constant.**
The map is discovered at boot (which is required anyway, since one binary has
to run on everything from a 130XE to a 1 MB board) and the trampoline goes
through a table built then, or a `set_bank(n)` routine.

### An Axlon, and the probe for both (2026-11-16)

An Axlon (RAMPower and its successors, to 4 MB) does not use PORTB at all:
a write to $CFFF picks the 16 KB bank in $4000-$7FFF, bank 0 being main
memory, so bank n IS register value n.  Altirra models it so (its MMU: the
register heard while the OS ROM is in, which gem4xe always has; PORTB's
own extended RAM wins when PORTB enables it).  `b6_probe`
(`src/sys6502/bank6502.s`) now looks for both:

- **PORTB** as before: the 64 values with bit 4 clear, the distinct banks
  kept -- at most 64, 1 MB.
- **An Axlon**: 255 down to 1 each write their number at $4000, so every
  alias writes before the bank it aliases; then 1 up are read back until
  one does not hold its own number.  With no Axlon the register is ROM,
  every write lands in main, and bank 1 reads main's marker: none.
- **The larger is taken**, and `b6_kind` says which ('P' or 'A').  On an
  Axlon's machine the probe then rewrites every bank switch in place:
  each is a public `b6sw_*` label on `LDA b6_portb,X/Y : STA PORTB`, and
  becomes `TXA/TYA : NOP : NOP : STA $CFFF` -- no table, two cycles more
  than the indexed load.  `tools/bsp6502/mkxex6502.py` writes the list of
  sites into `b6_sites` in the image, checking each one's bytes, and the
  probe checks them again.  A machine with both keeps only the larger
  kind (a 1088K board beside a 4 MB Axlon runs on the Axlon's 255 banks).
- **The far heap follows**: up to 255 banks, (255 - 17) / 4 = 59 far
  banks of 64 KB.  `fmap` took far banks to 15 only (its index arithmetic
  stopped at a byte there); it now takes them to 64 and stops on a carry
  instead.  The allocator still prefers the first megabyte, as it does on
  the Rapidus, so test-f6 writes the heap's last bytes on purpose.

**Found on the way: the probe was wrong on a 130XE.**  Its code and its
variables were in $A000-$BFFF, and a PORTB value it tries may map BASIC
there; it then read its own table under BASIC to put main memory back,
wrote a BASIC byte to PORTB, and switched the OS out.  1088K boards never
map BASIC with those values, so every gate passed.  The probe's code is
now in section `b6init`, which every link puts in Low, and while a value
is being tried it reads only its zero-page copies.

**Gated** (`make test-p6a`, `make test-f6a`): a 130XE with a 4 MB Axlon --
four PORTB banks, 255 Axlon ones, the MiSTer Atari800 core's largest --
runs test-p6 whole, pixels and all, and test-f6 with 63 far banks and the
last one written.  Broken on purpose: the switches not patched; main put
back from the table (the 130XE bug); fmap's old limit of 15.  Altirra's
command line gave `--axlonmemsize 4096K` 7 bank bits, the same as 2048K
(Windows and SDL front ends and the bridge alike; only its menu used 8),
so the gate AltirraSDL carries the fix, ilmenit/AltirraSDL#114; on an
unfixed one test-p6a finds 127 banks and fails.  And a launch with a memory size other than 1088K does not boot a disk
given with `--disk` -- it starts the Memo Pad -- so these gates boot
theirs through the bridge.

### The contention

**`$4000-$7FFF` is the contention.** It is the only switchable window, and
gem4xe currently runs a launched application there. Either the application
moves out of it — or applications are banked too. **There is nowhere for
it to move to.** `$A000-$BFFF` looked like the answer until the linker map
was written against a real machine: SpartaDOS X is a *cartridge* and that
is where it lives, so on the DOS this project targets those 8 KB do not
exist. The choice was never 14 KB against 8; it was banked or homeless.

**Decided (2026-09-17): applications are banked.** An application gets a
bank of its own rather than a slice of a shrinking resident pool, which is
*more* room than it has today, not less; the alternative spends the one
window on GEM and then rations what is left. It also makes each map a
whole bank rather than a negotiated carve-up, and it is the shape a
multitasking AES would want anyway, where each process holds its own bank
(`gem4xe-multitasking-request`).

Bank `$00` is already 95.5% and 84.9% full in its two resident memories,
and a banked build needs *more* resident space, not less — for the
trampolines and the bounce buffers. The 2 KB freed by `zwin` is real; the
8 KB at `$A000-$BFFF` is not (the cartridge). What is actually available
is `$8000-$9BFF`, the 7 KB the far-code staging buffer gives back — **and
on a machine without a VBXE the ANTIC framebuffer wants exactly that**,
6,720 bytes of it. So a VBXE build has room for the C stack and heap up
there and an ANTIC build does not.

### What banking the application costs

**Only one thing is mapped at a time**, so GEM's code and the application
are never both reachable. Every call between them switches the window, and
the trampoline that does it is resident in bank `$00`.

**The copy-in must happen on the application's side of the switch.** This
is the detail to get right: an application's parameter block lives in the
application's bank, so the trampoline must copy it into resident memory
*before* it switches the window, and copy the results back *after* it
switches home. `src/sys/abi.s` already has exactly this shape for a
different reason — it copies the block while the caller's data bank is
still addressable — so the 6502 version is the same discipline with PORTB
where the '816 has DB.

**GEM's own fourteen banks call each other too**, which is the larger
cost, not the application boundary. That argues for partitioning by call
locality rather than by source file — the VDI core and its device, the
object library (`objc`/`graf`/`grlib`, which recurse), the window and
control managers, GEMDOS — so the dense clusters sit inside one bank and
the trampolines carry only the traffic between clusters.

**The hottest code wants to be resident, and the room is tighter than it
first looked.** `zwin` gives back 2 KB and the staging buffer gives back
`$8000-$9BFF` — but on a VBXE-less machine the ANTIC framebuffer takes
6,720 of those 7,168 bytes, so what is left for the trampoline table, the
bounce buffers and the innermost loops is `$2000-$3FFF` and very little
else. That is the budget to design against, not the optimistic one.

## Still open
- **How the banked code model is selected.** `_JmpInline24`/`_JmpInd24`
  exist; nothing found here reaches them from C. That is a one-line
  answer for hth313 and it decides whether gem4xe writes its own
  trampolines or uses his. Worth asking with these measurements attached
  — it is a concrete report, not a feature
  request, and it pairs with the 6502 board support already offered on
  Calypsi issue #33.
- `cc6502` accepts `__far` and **silently ignores it** with a warning.
  `src/portab.h` already funnels everything through `FAR`/`NEAR`/`TINY`, so
  the seam exists — but a 6502 build must define them away deliberately and
  compile with unknown-attribute warnings as errors, or every far pointer
  quietly becomes a near one.

## The survey (2026-11-04)

`tools/bsp6502/survey.sh` compiles every C file of the system with
`cc6502 -O2 --core 6502`, through a 6502 block in `src/portab.h` that
defines `FAR`, `NEAR`, `SIMPLE_CALL`, `TASK` and `SAVEDS` away.

- **All 78 files compile, with no errors and no warnings**: the kernel,
  the VDI and its three devices, the AES, the desktop, the application
  kit and the applications, 47,864 lines.  The C really is portable C.
- **That is not a working build.**  There are **889 `FAR` uses**, and each is
  a place where the 65C816 build reaches memory above bank `$00` with a
  24-bit address.  A 6502 has none, so each one needs a banked accessor or a
  design that keeps the data in bank `$00` -- the far heap, the far object
  trees, the far code, the VBXE window.  The heaviest: `sdfs.c` 100,
  `doscmd.c` 91, `gemlib.c` 68, `deskwin.c` 55, `objc.c` and `menu.c` 37.
- **8,322 lines of 65C816 assembly** need a 6502 version or no version.
  About 4,500 are G4DOS and the cartridge (`fdos.s`, `cart*.s`); the
  kernel's own are about 2,000 -- `cio.s`, `irq.s`, `abi.s` (the COP gate,
  which on a 6502 becomes a `jsr` through a resident vector), `ctx.s`,
  `sei.s`, the arithmetic helpers, `crt_atari.s`, `farload.s`.

## Step 1: the VDI, banked, on a stock 6502 (2026-11-14)

**It did not fit unbanked.**  The VDI and the ANTIC device are 51.5 KB of
6502 code (vdi.c 31 KB, dev_antic 7.2, antic 7.0): 1.37x the 65C816's
37 KB.  A stock XL with DOS, the OS ROM and ANTIC's 7.7 KB screen has
about 32 KB.  The user chose to bank from the start rather than trim the
VDI to fit, so step 2's banking came first.

**The pieces** (`tools/bsp6502/`):

| | |
|---|---|
| `gem6502.scm` | the map: resident $2000-$3FFF and $A000-$BFFF; the window $4000-$7FFF as five MEMORIES of the same addresses, each scattered to its own store ($10000 + (n-1) x $4000), so a section names its bank and the linker does not choose |
| `bankasm.py` | each banked file compiled to assembly and rewritten: every JSR, JMP, `.word` or `#.byte` naming a function in another bank goes to a veneer instead; public functions become `F__b` with the veneer as `F`; statics reached from another bank get a file-unique alias |
| `bankcheck.py` | three checks, because no one source sees everything (below) |
| `mkxex6502.py` | the binary file: resident segments, then INITAD `b6_probe`, then per bank a one-byte `b6_next`, INITAD `b6_sel`, the bank's segment; INITAD `b6_main`; RUNAD |
| `src/sys6502/bank6502.s` | the trampoline `_bcall` (A and `_Zp` pass through both ways; X and Y are a call's to destroy), and the PORTB probe: every value with bit 4 clear, kept when it maps RAM across the window, leaves the resident sentinel at $A000 readable, and aliases no keeper |

The C needed only two `BANK_TEXT("…")` cuts in vdi.c (39 KB without
cross-call is three banks).  Nothing else in the shared source changed:
the 65C816 `vdi.o` is byte for byte the same.

**What the toolchain did that had to be found** -- each would have been
a confident wrong answer:

- **The optimiser's cross-call fragments ignore the section pragma.**
  `--no-cross-call` keeps code in its bank: 6.6 KB of shared fragments had
  gone resident, and vdi.c grows from 31 to 39 KB without them.
- **The link map names global symbols only.**  A call to a static
  function appears at neither end, and the map shortens lists to "... 8
  more" unless the link is `--verbose`.  So a map-only checker passed a
  build in which `vdi_v_gdp` (bank 3) called `fill_perimeter` (bank 2)
  directly, and the CPU jammed on bank 3's bytes at that address.
- **An address is not a name.**  Two banks' functions start at the same
  address often -- $4000 above all -- so a cross-bank call there looks,
  in the linked bytes, like a call to the bank's own function.  Hence the
  third check, by name, on the assembly.
- **as6502 reads `/* */` inside `;` comments.**  `--assembly-source`
  copies the C in as `;` lines, so a C comment over two lines after
  `static WORD cur_drawn;` swallowed the label between them: "undefined
  symbol".  bankasm drops those lines.
- **The optimiser merges identical function tails across functions** and
  across sections: `jmp ?L4340` from bank 2 into bank 3's last two
  instructions.  bankasm copies such a tail into place, and refuses one
  that is not a straight run.
- **The probe's results must be `noinit`**: they are filled during the
  load, before the C startup that zeroes bss.

**The checks** (`bankcheck.py`): the map's cross reference (globals,
`--verbose`); the linked code (every JSR/JMP into the window from resident
code, or to an address another bank's function starts at); the assembly
after bankasm (every reference by name).  `tests/host/test_bank6502.py`
holds all three to a fixture that must be refused as compiled and clean
through bankasm.

**The gate**, `make test-v6`: an 800XL's 6502, no accelerator, no VBXE,
1088K.  The probe finds 64 banks; the program draws test-m25's VDI calls
(a filled box and its XOR hole, text, clipped text, two raster copies) and
vqt_name; all 61,440 pixels match `tools/vdiref.py` on `devref.Antic()`.
Broken on purpose -- the trampoline not switching PORTB on a call -- it
never finishes and the gate fails.

**Not yet**: far memory (step 3; `src/sys6502/stub6502.c` answers no),
interrupts of its own, and a 6502 version of anpack's assembly (C here).
A 130XE's four banks do not hold the VDI alone: 1 MB is the machine.

## Step 3a: the far heap (2026-11-15)

`src/sys/farmem.c`'s allocator runs on the 6502 unchanged but for how it
reaches its block table: 25 uses became `FBE_*` macros, which on the
65C816 are the old far lvalues (the object is byte for byte the same) and
on the 6502 go through `far_get`/`far_put`.  The table stays block 0 in far
memory, so `tools/farref.py` models the 6502 heap with nothing changed.

`src/sys6502/farmem6502.c` makes far memory out of the PORTB banks after
the code's: a far address keeps the 65C816's shape, bank << 16 | offset,
bank 0 being near memory as it always was, and far bank k is four PORTB
banks.  The helpers are resident, work in pieces inside one 16 KB bank,
and always map the caller's bank back -- the caller may be banked code.
At 1088K and one code bank that is 15 far banks, 960 KB.

**The gate**, `make test-f6`: the allocator itself in a bank, so every
table access is banked code calling the helpers; eight requests, every
address as the model's; and the bytes -- across a 16 KB boundary, far to
far, a fill, a string, across a 64 KB far bank, bank 0 as near memory, a
bank's own code going on after the helpers used the window, and a marker
in each 16 KB piece of a long block.  Broken on purpose: no bank put back
stops the program; every piece of a far bank in one PORTB bank passed
every check until the last was added -- it read back through the alias.

**It runs on the MiSTer too**, the Atari800 core set to 6502 and 1MB:
`F6` prints its findings on E: (bits, far banks, the eight addresses) and
they are Altirra's; `V6` draws the same picture.  The loader can print
the probe's findings as it goes (`mkxex6502.py --report`), for a machine
whose memory nothing can read.

**Found on the way:**
- **cc6502's byte cast.**  `(uint8_t)(expr)` widened straight back to
  `int` is SIGN-extended, at every `-O` level: `(uint8_t)(0xC0 + k)`
  compared as `-64 + k`, and the distinct-pieces check failed with every
  piece right.  Plain `unsigned char` does the same; a `uint8_t` variable
  in between does not.  Shared C compiled for the 6502 needs a scan for
  this shape, as `make qscan` scans for the 65C816 compiler's.
- **A DOS that uses extended memory.**  The fixture DOS 2 variant, DOS
  II+/D 6.4, does (PORTB was once found at $87, a bank in, before the
  probe ran).  On the MiSTer's real SIO a bank's segment stopped loading
  under it, silently; Altirra's SIO patch hid it.  The 6502 test disks are
  MyDOS's now.  And the probe takes every bank it finds: a DOS's RAM disk,
  or SpartaDOS X's buffers, would have to be left out of it.

## Step 3b: the VDI's far reads (2026-11-15)

The VDI read some bytes straight through far pointers: the face's strip
(a loaded face is in far memory), the buffer it builds text at twice the
face's size in (`far_alloc`'s), and a raster's source (a form's
`fd_addr`, an icon in far memory).  On the 6502 such a pointer is 16 bits
and the bank is cut off.  `src/portab.h` now names what these are,
`far_src8`: on the 65C816 the same far pointer as before, on the 6502 the
24-bit address itself, read through `far_read8` (`FAR_RD8`, and
`FAR_IDX8` for a subscript).  The 65C816's `vdi.o`, `antic.o`,
`dev_antic.o`, `dev_vbxe.o` and `dev_print.o` are byte for byte the same.

The ANTIC device's `dev_raster_1bpp` brings each row it draws into a
near buffer on the 6502 (`far_get`, from the byte the first bit is in to
one past the last, which `antic_raster_row` may read), and draws it from
there; `dev_raster_form` reads its source with `FAR_IDX8`.  The 6502's
glyph packer (`src/sys6502/anpack6502.c`) reads a face that is in a bank
through `far_read8`.

`V6` now has the far heap: `src/sys/farmem.c` in a sixth bank, the
resident helpers, `farmem_probe` before the VDI (14 far banks at 1088K).

**The gate**: `test-v6` draws "BIG" at twice the face's size, which the
VDI builds in its far buffer, and holds it to the model with every other

## Step 4a: veneers in the caller's bank (2026-11-15)

Step 4's first job is resident memory, and the veneers were the biggest
thing in it after the code: 6 bytes each (`jsr _bcall`, the target, its
bank), one for every public banked function, all resident -- 1,668 bytes
in `V6`, and the AES would have added some 300 more.  But `_bcall` reads
the veneer's three bytes before it maps the target's bank, so a veneer
can sit in the CALLER'S bank as well as anywhere resident.
`tools/bsp6502/bankasm.py` now does this with an index of the whole
program -- which bank each public banked function is in, made from every
banked file's assembly (`build/b6502/v6.idx`) -- so a file knows where
another file's functions are:

  - a call within one bank goes straight to the function, no trampoline,
    across files too (it used to go through the resident veneer and
    `_bcall` even then);
  - a call from another bank goes through a veneer in the caller's bank;
  - only an address taken -- a table of handlers, a device's functions --
    or a call from resident code needs the resident veneer, and each of
    those is a section of its own now, so the linker drops the unused.

`V6`'s resident code went from 6,733 to 4,567 bytes in Low and its
veneers from 1,668 to 618 bytes; HiRam lost 189 bytes it no longer needed.
The file shrank from 122,486 to 92,884 bytes: the one veneer fragment of
each file had kept every public function it named alive, called or not,
and the linker now drops the functions the program never calls.

`tools/bsp6502/bankcheck.py` lets a veneer in a bank refer to another
bank (the map check), does not decode its data (the code scan), and with
the index refuses a direct call to another file's function in another
bank (the assembly check).  `tests/host/test_bank6502.py`'s new
`AcrossFiles` holds all of it with two files, and each half was broken
on purpose: direct calls off -- `test_same_bank_is_direct` fails; bank
veneers off -- two tests fail.  `test-v6` with the bank veneers' bank
byte wrong stops at stage 2.

## Step 4d: the context switch and the interrupts (2026-11-15)

`make test-c6`: two contexts taking turns on a stock 6502, test-m27's
runner (`src/c6_ctx.c`) on the 6502's terms. The design is the 65C816's
(`src/sys/ctx.h`): contexts share the stacks and take turns on them, a
parked context's extent copied to far memory and back to the same
addresses. A 6502 program has two stacks, and a context parks both:

- **page 1**, the 6502's own: return addresses, and under every call
  into a bank the caller's bank, which `_bcall` pushes there -- so the
  banks a context is nested through travel with it for nothing;
- **Calypsi's C stack**, a software stack under `_Vsp`: frames, locals
  and the registers each function saves.

`src/sys6502/ctx6502.s` pushes the compiler's register file (`_Zp`'s 48
bytes, `_Vsp`, `_Vfp`, `_Temp`: 54, checked against the linker's own
bounds at start-up) and `b6_cur` onto page 1, has both extents parked,
moves S and `_Vsp` together with interrupts held, has the incoming
extents copied back, maps the incoming context's bank and returns into
whoever parked it. `src/sys6502/ctx6502.c` does the bookkeeping, both
extents in the context's one far buffer, page 1's first. The 6502's CTX
has two words more (`vsp`, `vlen`; `src/sys/ctx.h`), 34 bytes.

**Only the assembly is resident.** The C half is 1 KB, and resident
memory had 690 bytes: it is in a bank (`evt` in A6, `far` in C6). That
is safe because its calls go through `_bcall`, which pushes its return
and saved bank below S, never inside an extent being copied, and it
touches only resident memory and far memory through the resident
`far_*` helpers. A6's process records grew by 32 bytes with the record,
and the boundary between Low (code) and LowRam moved down a page into
what the C half gave back; the linker places a section in one memory
whole, so `zwin` could not have spilled into ScreenTail.

**The gate**: the turns in the order asked for, each in its own bank
(`b6_cur` at every turn: a context resumed in the wrong bank would run
the middle of the other's code), and six frames whose locals survive a
switch from the deepest. A park costs 107 bytes at the deepest, both
stacks; a turn goes 14 bytes into page 1 at most. Broken on purpose:
with the C stack not copied back three levels lose their locals; with
the incoming bank not mapped back the program never finishes.

**The interrupt handlers** (`make test-i6`; `src/sys6502/irq6502.s`
and `.c`). The 65C816 copies the OS ROM under itself because its native
vectors were never filled (`src/sys/irq.h`); a 6502 takes the ROM's own
vectors, and the OS, its CIO and the DOS stay beside GEM. So the handlers
chain the OS's RAM vectors: the immediate VBI (`VVBLKI`, through
`SETVBV`; it runs even while SIO holds CRITIC) for `irq_frames` and the
triggers' ring, then on to the OS's; and `VIMIRQ`, before the OS's
dispatch has pushed anything, for POKEY timer 1 (the pointer sampler)
and the keyboard, acknowledged as the OS does, everything else handed on
with every register as it came. `irq.how` is the new `IRQ_OS_CHAINED`,
and the VDI's consumers, which ask only that it is not `IRQ_OFF`, are
unchanged.

The sampler runs at ~500 Hz (divisor 127), the rate `src/sys/irq.c`'s
own rule gives a 1.79 MHz CPU. Measured: at ~1 kHz the handler's ~200
cycles took 17.6% of the machine, ANTIC's DMA and all; at ~500 Hz 8.9%;
and 6.3% once the decode is skipped when the port's lines are as they
were, which is every sample of a still pointer. While installed the
keyboard is GEM's: the OS never sees a key, so CH stays empty (nothing
of GEM's reads E:) and the VBI handler holds ATRACT at zero, or the
OS's attract mode would start nine minutes after the last key it saw.
`irq_remove` gives both back. Not yet: `irq_clock`, which nothing on the
6502 calls before GEMDOS does, and the handlers in A6, which gets them
with the input poll.

**`test_sei`** forbids an SEI in the 65C816's native mode (an emulator
fault, `src/sys/sei.s`); a 6502 has no native mode, and
`src/sys6502/`'s assembly is outside the rule.

loop waits on a message and a 100 ms timer.  Nothing in the AES changed:
the round robin (`src/aes/proc.c`), the context switch on both stacks
(step 4d) and the event code are the 65C816's.

Its entry is its address, taken, so `tools/bsp6502/bankasm.py` gives it a
resident veneer -- the bank the first switch finds in the window is
whatever the application last had, and the veneer maps the accessory's.

`make test-e6` holds it, with everything the gate checked before running
beside it:

- it parked (`$060B` 'P', `proc_n` 2);
- it has turns while the application sits in its own wait: its timer
  answers 14-15 times in two seconds, about 30 turns handed over;
- a key P makes the application send it `A6_PING`; it answers `A6_PONG`
  to the sender with the ping's number and the pid the AES says is
  running, its own: two pings come back numbered 1 and 2, from pid 1.

Broken on purpose: without `acc_start` the gate fails twice (not parked,
and its counters are not in the program); with the answer sent to itself
instead of the sender, the PONG check fails.

**The switch is not cheap.**  A 100 ms timer answering 15 times in two
seconds says a round trip -- the application's stacks parked into far
memory, the accessory's put back, and the same again -- costs about two
frames on a 1.79 MHz 6502.  It is `far_put`'s and `far_get`'s byte copies
through the bank window, the same accessors that a first timing of A6
(a menu drop 920 ms, a window close 2.5 s) found doing a quarter to a
third of the work.  One effect showed in the gate:
the trak-ball's counts become pixels on the application's turns, so the
last of a burst lands a little later, and the gate now waits for the
pointer to stop before it reads it.

**PAL and NTSC.**  Asked whether NTSC is faster: it is not, on this
screen.  The CPU's clock is 1% higher, but ANTIC fetches the hi-res
screen 60 times a second instead of 50, and the cycles it takes are the
CPU's.  Timed in milliseconds, A6's menu drop is 920 ms on PAL and
1000 ms on NTSC, picking Open 280 and 333.

Running the gate on NTSC found a fault that was PAL's: A6 installed the
interrupt handlers after `ev_init`, the other way round from
`src/gem.c`.  `irq_install` is what finds the video standard, and
`ev_init` takes its tick length from the VDI, which answers from
`irq.pal` -- so a PAL machine's 20 ms tick was taken for NTSC's 17 and
every timer and the double-click window ran 18% long.  `a6_aes_up` now
installs them first, and `make test-e6` checks the tick (20 ms, the
double-click window 11 ticks) and `make test-e6n` runs the whole gate on
an NTSC machine (17 ms, 12 ticks).  With the old order put back the PAL
check fails.  The trak-ball check now calls the pointer still after 10
quiet frames, not 4: with a switch to the accessory and back taking
~40 ms, the application's polls can be more than four of NTSC's frames
apart.

## Speed: a first pass (2026-11-16)

Timed on a stock 6502 at 1088K, PAL, by the screen's last change after
each input, and profiled with the CPU history so that code in the bank
window is named by the bank PORTB had in (each `STA $D301` followed):

| | before | after |
|---|---|---|
| point at File: the menu drops | 920 ms | 480 ms |
| pick Open | 280 ms | 80 ms |
| a window's close and the redraw under it (work, not waiting) | 84 frames | 45 frames |

NTSC is no faster: its CPU clock is 1% higher, but ANTIC draws 60
screens a second, not 50, and every hi-res line it draws takes cycles
from the CPU -- the menu dropped in 1000 ms there before this pass.

**The far helpers in assembly.**  `src/sys6502/far6502.s` has
`far_read8`, `far_write8`, `far_rd16/32`, `far_wr16/32`, `far_get`,
`far_put`, `far_fill`, `far_strget` and `ob_rd16/32`, `ob_wr16`; the
rest stays in `farmem6502.c`.  In C they were a quarter of the busy
time: each field of each object went through 32-bit arithmetic, a stack
frame and a two-byte `memcpy`, and each string through `far_read8` a
byte at a time, mapping and unmapping for every one.  Now a field is
mapped once and read in place (through `far_get`'s piece-by-piece path
only when it straddles the end of a 16 KB piece), a string is walked by
a pointer that is remapped only where it crosses into the next piece,
and a block goes a page at a time.  They cost 192 bytes of resident
memory net.  `make test-f6` gained a second status byte for them, $0605:
16- and 32-bit fields at every offset from 3 before a piece's end to 1
after, a string across a piece's end and cut short by its maximum,
object fields and the carry into the next far bank, and all of it on
near memory.  Broken on purpose -- no straddle check, no remap at a
piece's end, no carry -- each of those failed.

**The ANTIC driver's inner loops**, in `src/sys6502/antic6502.s`, in the
ANTIC bank's own section (`antic`), so they cost no resident memory:
the middle of a filled row (`an_fill6`: cc6502 made the 65C816's word
stores 16-bit pointer arithmetic, 50 cycles a pair; now 13 a byte), and
the pointer's save, restore and paint (`an_cblk6`, `an_cpaint6`: each
row's address was a multiply and the form's shift a 32-bit shift by a
variable, a runtime loop -- the pointer's hide and show around every
draw were a tenth of a window's close).  The clipping stays in C.  The
pointer was held to the C version by drawing it at 342 places, every
shift and both edges of both axes, in an image built each way: the 342
screens and the screen left after are identical; with the outline
painted in the wrong colour all 342 differ.

**The close box's "delay" is GEM's.**  A press on a close box reaches
the AES 10 frames late when the application is waiting for up to two
clicks, as A6's is: a first press is held for the double-click time
(11 ticks) to count a second, in `src/aes/event.c`'s `b_click`, as in
every GEM.  A first timing seemed to show a 35-40 frame delay only
after a menu pick; that was the bench timing the screen, and with the
AES's state logged frame by frame the two cases are the same.

What is left, by the history: the rectangle fill's per-row work in C
(14%), the far helpers still (~15%, most of it `fmap` and the object
address), cc6502's stack-frame helpers (~11%), `_bcall` (7%) and the
trak-ball's sampling interrupt (6%, as on the 65C816).

## Step 5: an application in a bank

**What an application is.**  A program built with the kit, linked whole
into one 16 KB bank at $4000-$7FFF -- code, constants, data, bss and its
heap (`src/app/gemapp6502.scm`) -- with a header at $4000 that the loader
checks and an entry the system calls.  Its own start-up
(`src/app/crt6502.s`) initializes its sections with the runtime's
`__initialize_sections`, as Calypsi's start-up would, and calls `main`;
it does not touch either stack.  It RUNS ON THE SYSTEM'S STACKS: page 1
and the C stack under `_Vsp` are resident and shared, and a process
switch already copies both in and out (step 4d), so an application's
locals are near memory like anyone else's.  The pseudo-registers at $80
are shared by the calling convention; zero page beyond them is the
system's, and a program that asks for some is refused at its link.

**How it calls.**  The kit's `vdi_call` and `aes_call` (on the 6502,
`src/app/gemabi6502.s`) jump to the gate at a FIXED resident address,
$2000, with the parameter block's address in `_Zp0-1` and the call's
letter, 'V' or 'A', in A: the COP's signature byte, as a register.  The
gate records the caller's bank (`b6_cur`: the window is the
application's while it runs) and enters `gem_entry` through a veneer;
`_bcall` puts the application's bank back on the way out, and a process
switch inside the call carries it (`ctx_switch` saves `b6_cur`).

**Its addresses.**  On the 6502 every pointer in the kit is 16 bits, so
the blocks hold window addresses.  `abi.c` turns one in $4000-$7FFF into
the far address of the caller's bank -- far bank k, piece p, as
`farmem6502.c` numbers them -- and leaves any other alone (a local on
the shared C stack is near and stays near).  The block and its arrays
are then read and written with `far_get`/`far_put`, as the 65C816 reads
a far caller's: the same entry discipline (copy in, call, copy out),
and nothing of the application's is touched while another bank is in.
An address the AES hands BACK (rsrc_gaddr's) goes the other way when it
is in the caller's bank; one elsewhere stays far, and a 6502 program
cannot follow it -- the kit's comment in `src/portab.h` says so.

**5a, the gate -- DONE 2026-11-16** (`make test-p6`).  What was built:

- **`src/sys/abi.c` on the 6502**, in a bank of its own (`abi`, the
  17th).  Its 83 far accesses are explicit now: a caller's word array
  (its global, a message buffer) is `ABI_WP`, a far pointer on the
  65C816 and a far address on the 6502, read and written through
  `ABI_W`/`ABI_SETW`; a tree is `OBTREE`; the two entries have a 6502
  version each (`vdi_entry6`, `aes_entry6`) that moves every array with
  one `far_get` or `far_put`, with the middle of an AES call in
  `aes_core`.  The 65C816's entry keeps those lines inline, as they
  were: split out on both machines, test-m11 found appl_getinfo's last
  two words -- the two pointers ap_getinfo is passed on the stack --
  coming back zero on the 65C816, with the same values reaching crysbind
  one call deeper.  Not reduced, so no compiler bug is claimed; the
  65C816's code is the code it was.  `make farscan`
  reads `abi.c` now and finds nothing.
- **The translation**, `win_far`: a window address becomes far bank k,
  piece p, of the caller's bank.  It is done to the block, its arrays,
  every `addr_in` -- and to the one address an AES call carries in

- **Programs' banks**: far bank 1 (four PORTB banks after the code's) was

  (`mkxex6502.py --bank 18=build/p6prog.elf`); since 5b-1 A6 reads it

- **The gate** at $2000 (`src/sys6502/gate6502.s`, a `gate` section the
  link file fixes there) and `p6_ven`, the program's entry: a veneer in

- **What `abi.c` reaches for that the 6502 has not got** --

  `gem_badop` names the opcode, never pretending.
- **The kit's 6502 half**, in `src/app/`: `gemabi6502.s` (the gates jump
  to $2000 with the letter in A), `crt6502.s` (the header "G6", format
  1, `JMP start`; sections initialized; no stack touched) and
  `gemapp6502.scm` (one bank; zero page only the pseudo-registers, which

**Resident room went UP**, from 97 bytes free in Low to 375, with the gate

names its label -- the tables all come at the end of a file, so the
section before one is nobody's; the first version took that one, and

**Two things found on the way.**  The test program's window first showed

**5b-1, the read -- DONE 2026-11-16** (`make test-p6`, which now loads

- **CIO on the 6502.**  `src/sys/cio.c` unchanged, in bank `far` beside

  that maps its own.  There is no mode to switch, as there is on the

- **The file**, `.G6A`: the program's bank as one image from $4000, its

- **The read** (`prog_load`, `src/a6_evt.c`): 256 bytes at a time into

  more than a bank is refused.  $060D is CIO's status, $060E-F the bytes.
- **The POKEY resync**: `irq_pokey_resync` on the 6502, as the 65C816

**5b-2, the program's bank from the heap -- DONE 2026-11-16**
(`make test-p6`).  No banks are set aside for programs any more: far
bank 1 is the heap's, and a program's bank is a block the heap hands
out, as the 65C816 hands out a program's memory.

- **`far_alloc_piece`** (`src/sys/farmem.c`, the 6502's only): 16 KB on
  a 16 KB boundary, which is one PORTB (or Axlon) bank whole, since far
  bank k, piece p is `b6_far_base + (k-1)*4 + p`.  **`far_piece`**
  (`src/sys6502/farmem6502.c`) names that bank, for the veneer's bank
  byte.  `win_far`/`win_near` (`abi.c`) needed nothing: they already
  work from the caller's bank, whichever it is.
- **The load** (`prog_load`, `src/a6_evt.c`) takes the block for a new
  owner (`far_new_owner`), reads into it and checks the header; on any
  failure it gives the owner's blocks back.  No bank free answers $C8,
  not a .G6A $C9.  `p6_slot` keeps the address, for the gate.
- On a 1088K machine the program lands at $014000, piece 1 of far bank
  1: piece 0 holds the heap's own table.  So the gate exercises a piece
  that is not the first.

The gate also checks the block: 16 KB-aligned, in the heap, and the
veneer's bank byte the bank it names, computed in Python from the
numbering above, not from the code's.  Broken on purpose it fails: with
the block only 4-aligned (the machine is lost), and with `far_piece`
leaving the piece out (bank 18 for 19, the far stop at $0604).

**5b-3, a program's resource, and its own C stack -- DONE 2026-11-17**
(`make test-p6`).  `rsrc_load` puts the resource in the far heap, as the
65C816 does for a large-data program; it does not go in the program's
own bank, which would cap code plus resource at 16 KB and would never
hold the desktop's.

- **A tree is a far address** on the 6502: `GEMTREE` in `src/app/gem.h`
  is `uint32_t` there and `OBJECT *` on the 65C816, so the 65C816's kit
  is what it was.  Every call that takes a tree takes a `GEMTREE`;
  `rsrc_gaddr` answers one (`GEMADDR`); `TREE_OF(array)` makes one of an
  OBJECT array in the program's bank, `OB_ADDR(t, i)` is object i.
- **`far_fetch` / `far_store`**, the kit's, copy between far memory and
  the program's own: through the gate as `'F'`, a five-word block --
  fetch or store, the far address, the near one, the length -- which
  `abi.c`'s `far_entry6` serves with `far_copy`, the near side made far
  by `win_far` like any address a program passes.  Not a GEM call, so
  not counted as one.
- **`rsrc.c` on the 6502**, in A6's bank 18 (`rsrc`): its variables are
  that bank's (`RS_BSS`, `BANK_DATA`); the desktop's resource cache is
  left out (it needs a whole-file read, a 32-bit hash and a span copy
  in resident code there is no room for); a 6502 program always loads
  far (`abi.c` passes 1); `sh_cioname` is a stand-in until GEMDOS, the
  flat DOS's rule (`abistub6502.c`).  New-format resources (colour
  icons) are refused: they need the pool.
- **P6PROG.RSC** (`tools/p6rsc.py`): a box, a string, a button.  The
  program reads object 1 and its string through `far_fetch` and draws
  that string where it drew its own (so a wrong read shows in the
  pixels), stores object 2's state and reads it back, and asks the AES
  for object 2's offset.  The boot disk is `--compact`ed: MyDOS's
  directory was full.

**THE C STACK OVERFLOWED, and had since 5a.**  The system's C stack is
1 KB of resident memory (`cstack`, $3BF3-$3FF2 in A6), and a program
ran on it too.  Measured with conditional breakpoints on the runtime's
stack allocators (`BP_SET ... condition=dw($b0)<$3c80`), `_Vsp` went to
$3BA2 -- 81 bytes below its floor, onto `pal_req` and the VDI's
workstation table -- on A6's text path: `objc` → `gr_gtext` →
`vdi_v_gtext` (a 123-byte frame: cc6502 had inlined `run2` and its
89-byte row buffer, and it ignores `__attribute__((noinline))`) →
`and_text_run` → `antic_text` (a 41-byte row buffer).  test-p6 passed
by luck; adding the resource calls moved what was hit, and the machine
hung in the VDI at places that moved with every build.  Three changes:

- **A program has its own C stack**, at the top of its bank: a
  `cstack` block in `src/app/gemapp6502.scm` (1.5 KB).  `crt6502.s`
  keeps the system's `_Vsp` (in `g6_sysvsp`, after the sections are set
  up, since that zeroes bss) and moves to its own; each call into the
  system (`gemabi6502.s`) moves back for the call and returns to the
  program's after.  The 65C816 gives a program its own stack too.  A
  local's address is now a window address, which `win_far` already
  turns into the program's far address.  The gate itself is unchanged:
  resident code had 9 bytes free.
- **`vdi.c` is compiled `--no-inline` on the 6502**: `vdi_v_gtext`'s
  frame is 0 bytes, and the three VDI banks are 590 bytes smaller.
- **`antic_text`'s row buffer is bank data** on the 6502
  (`BANK_DATA("antic")`; only the resident packers touch it, with the
  bank mapped).

**The guard**: test-p6 paints the bottom 128 bytes of the system's C
stack before the program starts and wants at least 64 of them still
paint at the end; it finds 79.  With `vdi.c` inlined again it finds 3
and fails.  Broken on purpose otherwise: `far_entry6` with fetch and
store swapped stops the program at once.

### 5b-4: GEMDOS from a bank (2026-11-17)

A 6502 program's GEMDOS calls go through gate 'D' to `src/sys/gemdos.c`,
the 65C816's own, compiled for the 6502:

- **Its far memory through the window's helpers**: `rd16`/`rd32`/`wr16`/
  `wr32` are `far_rd16` and the rest on the 6502, and the block's
  arguments are read through them.  Its three constant tables are
  `FAR_816`, two of them `BANK_DATA` beside the one function that reads
  each (`gd_devnames`, `df_geom`).
- **An address argument is `arg_p`**: the same as `arg_l` on the
  65C816; on the 6502 `win_far(arg_l(off), gd_bank6)`, the bank the gate
  recorded, so a window address in the program's bank becomes its far
  one and a near or far one is left as it is (`win_far` and `win_near`
  are public in `abi.c` now).  Fgetdta answers through `win_near`.
  `gemdos_call6` takes the block's window address and the bank.
- **Three banks**: `gemdos` (19: names, open, the transfers, the
  dispatch), `gemdos_b` (20: the search, directories, drives, memory,
  the console, the clock calls), `gdos` (21: the handles, Fseek and
  Fdatime, with `dos.c`, `con.c` and `clock.c`).  A6 has 21 code banks;
  a program loads at $018000.  `dos_ident` and `gemdos_init` are in A6's
  start (`src/a6_tree.c`).
- **Not on the 6502 yet**: Pexec (a 6502 program is loaded by
  `src/a6_evt.c`'s `prog_load`; 5c), the control panel's calls, Psystem.
  GEM4XE.CFG is not read, so PRT: is `PRINTER=NONE`.  `irq_clock` is
  shared with the 65C816 (`src/sys/irqclock.inc`).
- **THE POOL**, a call's scratch: GEMDOS takes its path work (320 bytes)
  and its transfer slices from it and gives them back before it returns.
  On the 6502 it is a stack (`src/sys6502/abistub6502.c`) over the
  load-time code's 494 bytes, section `b6init` ($2021-$220E), dead once
  main runs.  It must be near and outside the window -- `far_get` and
  `far_put` map the far side into it -- and nothing may keep a block past
  its call, so rsrc.c's colour icons stay refused.  `sh_cioname` is
  GEMDOS's `gd_cioname` now.
- **Resident memory, again**: the veneers and tables needed 380 bytes
  and A6 had 36.  Page 5 and the top of page 4 ($0480-$05FF, which MyDOS
  leaves zero; its code is in $0400-$047F) became memory `Page5`, A6's
  own records in it (`a6_log`, `prog_queue`), and HiText took 224 bytes
  of HiRam; A6's menu strings went into its bank, copied through the
  stack.  HiRam has 8 bytes left, Low 99.
- **Two tools fixes**: cc6502 names a string literal after its text, and
  writes a backslash in it that as6502 then refuses ("\\*.*"); bankasm
  respells it in every file alike.  And `BANK_DATA` on a `const` is
  `rodata`, which bankasm now banks too.
- **The scans found a real one**: `gd_owned |= (uint8_t)(1 << iocb)`,
  into a 16-bit field, is $FF80 on the 6502 for IOCB 7 -- eight bits that
  never clear (b6scan).  The casts are 16-bit now.

**Gated** (test-p6, and test-p6a on the Axlon): the program calls
Sversion ($1500), Fsetdta on its own DTA and Fgetdta gives it back,
Fsfirst("*.RSC") finds P6PROG.RSC, Fopen gives a file's handle, Fread's
18 bytes are the file's, Fseek(0) and a read of 4 again, Fclose,
Dgetpath writes "" over a buffer of $FF, and a missing file answers
EFILNF.  The pool's peak is inside `b6init`, nothing refused, GEMDOS
counts the 11 calls and no unknown one.  Broken on purpose: `arg_p`
without `win_far` fails seven of them (Dgetpath's only since its buffer
is filled first: it passed on zeros).

**Not yet**: a program cannot hand Fread a far address -- the kit's
`void FAR *` is 16 bits on the 6502 -- so it reads into its own bank.
And GEMDOS's length for a DOS 2 directory entry is sectors times 125,
which on MyDOS's 256-byte sectors is half the truth (the 65C816 the same).

### 5c-1: programs of several banks (2026-11-17)

The desktop compiles to ~49 KB of 6502 code and 3 KB of data (measured:
deskwin.c alone is 21 KB), and a program was one 16 KB bank.  Decided
with the user: programs of several banks, not the desktop built into the
system, since every real application will need them too.

- **Where the data goes.**  A program's code can be in several banks,
  but only one is in the window at a time, and its data, stack,
  constants and veneers must be seen from all of them.  The only RAM
  outside the window with room is the 14 KB under the OS ROM ($C000-
  $CFFF, $D800-$FFFF).  So **the system runs with the ROM out** once it
  has started (`src/a6_tree.c`, `ram_vectors`): bit 0 clear in PORTB and
  in every `b6_portb` entry, so no bank switch brings the ROM back.  Then
  a program's pointers to that RAM are plain near memory to the system
  too -- its parameter arrays, strings, buffers.  Needs PORTB banks and
  RAM under the ROM: any XL/XE, or an 800 with an XL OS and PORTB (an
  Incognito).
- **The ROM comes in** for CIOV and SIOV (`src/sys6502/cio6502.s`, which
  puts PORTB back as it found it) and for an interrupt: the CPU reads its
  vectors from the RAM then, and `ram_vectors` writes `g6_nmi`,
  `g6_reset` and `g6_irq` there (`src/sys6502/gate6502.s`, resident).
  Each keeps A, X and PORTB, switches the ROM in and enters the ROM's own
  handler as the CPU would have -- the P the CPU pushed copied from the
  stack, since a PHP pushes B set and the XL OS reads that as a BRK --
  and restores all three after its RTI.  With the ROM in they never run.
- **What read the ROM**: `kb_translate` (`src/vdi/vdi.c`) reads the OS's
  key table through KEYDEF ($79).  It is copied to $FE00 under the ROM
  and KEYDEF pointed there -- the OS keeps it at $FEFE or $FB51 by
  version, and $FB51 is inside a program's RAM.  Nothing of the OS reads
  KEYDEF while gem4xe runs (its keyboard IRQ is taken first).  And
  GEMDOS's Fread/Fwrite handed a bank-$00 buffer straight to CIO, which
  runs with the ROM in: a buffer at $C000 or above goes through the pool
  slice now (`GD_CIO_CANNOT`).
- **Not on an Axlon**: its register at $CFFF is decoded only with the ROM
  in (AltirraSDL's mmu.cpp, as the hardware), so with the ROM out no bank
  switched and A6 stopped at its next veneer.  On an Axlon the ROM stays
  in, one-bank programs run as before, and A6 refuses one of several
  banks (status $CA).  Switching the ROM in around every Axlon switch is
  possible -- fifteen sites and resident bytes the 6502 build has not
  got.
- **A program of several banks** (`src/app/gemappm6502.scm`): code in
  banks 1..n (`BANK_TEXT("pbK")`), bank 1 starting with the header,
  "G6", 2; the link block the loader fills at $C000, veneers, runtime and
  constants to $CFFF; data, bss, heap and its C stack $D800-$FDFF;
  $FE00-$FFFF the system's.  `tools/bsp6502/bankasm.py --trampoline
  _pcall` banks it with the program's own trampoline
  (`src/app/crt6502m.s`), whose bank numbers are the program's, mapped
  through the link block's `g6_banks` to the system's bank indexes.
  `_pcall` must keep `b6_cur` true -- the gate maps back whatever it
  names -- so the link block carries the addresses of `b6_cur` and
  `b6_portb`, which `start` patches into `_pcall`'s instructions.
- **Format 2** (`tools/bsp6502/mkxex6502.py --g6a`): a header, the pieces
  under the ROM, the banks; A6 (`src/a6_evt.c`) takes n banks from the
  far heap, reads the pieces and banks through `p6_buf`, checks where
  each piece goes, and fills the link block.  One program of several
  banks at a time: nothing yet keeps a second copy of the RAM under the
  ROM.
- **Two linker traps** (Calypsi 5.18): a `root` section in a memory with
  `scatter-to` crashes ln6502 ("Placement.hs: Non-exhaustive patterns"),
  so the header is the head of the fixed `g6start` section; and two
  fragments of one section are not kept in order.
- **Resident memory**: the handlers took 88 bytes; Low has 4 left, HiRam
  7.  The loader's bank table went into page 5.

**Gated** (test-p6m): the load (every byte, three banks, the link
block), the ROM out (PORTB, the RAM vectors, KEYDEF and its bytes the
ROM's), calls across all three banks -- a chain with an initialised
global (26), mutual recursion ten deep (55), a table of function
pointers (107), a constant returned from bank 3, a bss count (17) -- and
the system with data under the ROM: appl_init, Fread into a buffer
there, an alert whose text is there answering Return with its second
button.  test-p6ma: refused on an Axlon, ROM in.  Broken on purpose:
`_pcall` not keeping `b6_cur`, 7 fail (it dies at its first call); the
ROM bit left in `b6_portb`, 10; without the Axlon refusal, 2; without
`GD_CIO_CANNOT`, Fread's bytes are zero.  test-a6, e6, p6, p6a pass with
the ROM out.

### 5c-2: far data in one source (begun 2026-11-18)

The desktop reaches far data in ~300 places -- its resource's trees,
strings and icons, the colour icons, its arena of FNODEs, DTAs and
buffers (~10 KB, more than a program's RAM under the ROM holds).
Decided with the user: a portable layer, not smaller 6502 limits.

- **gem.h's far accessors** (the kit's, for any program): `FPTR(T)`,
  `FP_OF`, `FIDX`, `FGET`, `FSET`, `FFLD`, `FDEREF`, `FNEXT`, `FCOPY`,
  `FGETS`, `fa_get`/`fa_put`/`fa_rd*`/`fa_wr*`.  On the 65C816 each is
  the expression it replaces: the desktop's and the kit's objects stay
  BYTE-IDENTICAL, which is how each converted file is checked (a
  one-character change makes the comparison speak).  On the 6502 they
  call `src/app/farm6502.c`, in the program's shared RAM, which maps the
  far piece into the window itself -- no system call -- and maps the
  program's bank back.  `FGET` picks its read by the field's type
  (`_Generic`): one 32-bit read cast to a byte keeps bits 8-15 on cc6502
  5.18, which b6scan caught.
- **The kit's far arguments**: every call with a `void FAR *` (Fread,
  Fwrite, Fsetdta, Mfree, Dgetpath and the rest) takes `FA_PARAM(T)`:
  `T FAR *` on the 65C816, a 32-bit address on the 6502, where a macro
  per call passes a near pointer as bank 0 and a far address as it is
  (`FAR_ARG`, by type).  So a 6502 program can Fread into Malloc'd
  memory now, and Mfree it.
- **The whole desktop converted** (2026-11-18): desk.h's declarations,
  then all five files, ~280 places, through `TGET`/`TSET` for its trees,
  `FGET`/`FSET`/`FARR` for its FNODEs, DTAs, WSAVEs and colour icons,
  `FAT`/`FPUT`/`FNEXT`/`FPUTN` for its far strings, `FINC`/`FDEC`/`FIDX`
  for every step through a far array (a 32-bit address adds bytes, not
  elements: nine `pf++` and six `pws++` were found by hand, as the
  compiler cannot), and `FMOVE` for the sort's far-to-far moves.  Three
  `rsrc_gaddr` targets were 16-bit `char *` -- on the 6502 it would have
  written 32 bits over them.  It compiles for the 6502 with no error, and
  its 65C816 assembly is the committed one's but for: a declaration
  emitted elsewhere (deskcmd.c), `inf_sget` calling `put_far`, which is
  `put_str`'s twin (deskfun.c), and `do_docu` titling the viewer from the
  near path rather than the far name, plus shared tails emitted in
  another order (deskwin.c).  `FARR` exists because `FFLD` of an array
  field is a pointer to the whole array on the 65C816.
- **b6scan now scans the desktop** (and farm6502.c), and found 38: every
  `FDEREF` -- behind `FAT` and `FNEXT`, so every far string compare --
  cast one 32-bit read down to a char, which cc6502 5.18 gets wrong as it
  did `FGET`'s; it picks its read by type now.  `FPUT` stores its value
  into a T first (a computed byte cast passed on widens wrongly), inside
  the 6502's macro, so the 65C816's code keeps its shape.

**Gated** (test-p6m): a Malloc'd block written through `FSET`/`fa_put` --
a record, one past the first 16 KB piece, 8 bytes across the boundary --
read back through `FGET`/`fa_get` and through the system's `far_fetch`;
Fread straight into the block and Mfree by its far address.  Broken on
purpose: `fa_put` not splitting at the boundary, 2 fail; `FAR_ARG`
truncating to 16 bits, 2.

### 5c-3: the desktop on the 6502 (2026-11-18)

The desktop runs on a stock 6502: its menu bar, its desk with a drive
icon per drive and the trash, and a double-click opens a window on a
drive, listed, sorted and drawn -- the same source as the 65C816's.

- **Eight banks** (`tools/bsp6502/rules.mk`, `build/desk6.g6a`, 89 KB):
  desktop.c, deskobj.c, deskfun.c in two and deskwin.c in three
  (`BANK_TEXT`, nothing on the 65C816), deskcmd.c with the kit's
  gemlib.c.  The far accessors and the cross-bank veneers made it ~80 KB
  of code, not the 57 KB first measured; the link file has eight banks.
  Its RAM under the ROM is 44% used, its shared code 63%.
- **Two disks**: A6 is 258 KB (21 banks) and the desktop 92 KB, more than
  a floppy; A6 looks for P6PROG.G6A on D1: and then D2:, and the desktop
  is on D2: (`build/a6d-desk.atr`), its resources on D1:.  The names are
  A6's bank data: resident memory had not the 14 bytes.
- **A6 as host**: `$060C` 2 at the go closes A6's two test windows and
  starts the desktop.  The shell buffer is served (`sh_get`/`sh_put`, a
  far block the system keeps) and `shel_write(SWM_NEWMSG)` answers 1.
- **THE DESK IS ITS OWNER'S** (both CPUs): a press on the bare desk, or on
  the desk while no window is open, went to process 0 -- the desktop on
  the 65C816, A6 here, so the desktop never heard a click.  WF_NEWDESK
  now records who set it, the bare-desk press and the "nothing on the
  screen" fallbacks go to `wm_owner(DESKWH)`, and setting it while the
  desk is on top hands the input over at once (with the desk on top a
  press is inside the control rectangle, which goes to the input owner,
  last decided when A6 closed its windows).  Found with two probes, which
  showed the press inside a control rectangle nobody had set -- the desk's
  own work area.

**Gated** (test-d6): loaded into eight banks, nothing stopped, nothing
refused, the input the desktop's once its desk is up; a double-click on
DISK D1: puts the window's title and information line in its memory, the
count and bytes of D1:'s files as the disk image itself says (sectors
times 125).  Broken on purpose: without the hand-over at WF_NEWDESK, 3
fail.

**Next**: what a usable 6502 desktop still lacks -- Pexec (no program
starts from it yet), the DOS command window, the control panel, colour
icons -- then its speed, then hardware (the MiSTer counts).

## ANTIC stays out of the bank window

Nothing ANTIC fetches may sit in $4000-$7FFF: it reads memory on its own
whatever bank PORTB has in, so a display list, screen, player/missile area
or font there shows whichever bank a DOS in banked RAM (SpartaDOS X) has
swapped in during disk I/O.  The ANTIC device's display list is at $8000
and its screen at $8100-$9EFF, the boot screen's fonts at $8000 and $8400,
and the pointer is drawn into the screen, so there is no PMBASE at all.
`tests/host/test_antic_window.py` holds all of it to the rule, with the
6502 link maps keeping $8000-$9EFF empty; each check was broken on purpose
in a copy (screen at $7100, font at $7800, a PMBASE writer, a map over the
screen) and failed.
