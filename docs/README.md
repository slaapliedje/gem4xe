# The notebooks

One document per phase, written as the work happened: what was built,
what was wrong on the way, and how it was found.  They are the reason a
bug that cost a day costs nobody a second day, so they record the false
trails as well as the fixes.  `../README.md` is the current state; these
are how it got there.

Read in order if you want the argument; jump if you want an answer.

| [phase41.md](phase41.md) | The call gates move to `COP #$56`, `#$41` and `#$44`, because drac030 pointed out that `$01` is Rapidus OS's own and `$80-$FF` are WDC's -- and the handler had been serving anybody's `COP #$01` as GEMDOS. A COP that is not gem4xe's now goes to Rapidus OS through its own vector when `@:SYSDEF` says it is there, and is refused when it is not; `.g4a` becomes format 3/4 so old programs are refused by name; the kit links assembly. | [phase42.md](phase42.md) | The rest of GEMDOS, for programs ported rather than written here: a VT-52 console drawn on GEM's screen through the AES's waist, read through the AES's own key wait; the ST's six standard handles with `Fdup` and `Fforce`, so a program's `Cconws` lands in a file; `Mshrink`, `Mfree` and `Mxalloc` on a bump heap whose blocks now know their size; `Tsetdate`/`Tsettime`; `Pterm`, which unwinds straight back to the loader; and `Pexec` mode 0, a child above its parent with the parent's handles and DTA kept aside. `make test-m32` runs a program that never calls the AES. | [phase45.md](phase45.md) | Auditing what the ENGINE serves rather than what the kit declares: `tools/opcodes.py` reads the dispatchers and opened at 63 of 79 AES opcodes, disagreeing with the header in both directions -- `WF_SCREEN` and `WF_OWNER` served and undeclared (so QED `#define`d them itself), `WF_BOTTOM` declared and unserved. Then the gaps: `objc_sysvar` (whose `AD3DVALUE` is 0 here, not EmuTOS's 2, because nothing draws a 3D border), `appl_find` (and the eight blank-padded characters `appl_find("")` would otherwise have matched), `appl_getinfo` (fifteen true answers, and the Compendium has its return value backwards), `appl_yield`, `graf_mbox`, `graf_slidebox`, `wind_new`. | [phase46.md](phase46.md) | The last ten opcodes, and **79 of 79**. Three of them are not Atari's calls at all -- `scrp_clear` is PC-GEM's, and `shel_rdef`/`shel_wdef` appear in Atari's own documentation only as a question `appl_getinfo` asks -- and are served anyway because both halves do something. `appl_read` could not be written without finding that `appl_write` copied eight words whatever length it was told, wrong in both directions. The four menu calls: `menu_popup` clamped in both directions where the ROM clamps neither, `menu_attach` writing into the application's string as the ROM does but checking the length first, and `menu_settings`, whose fifth number is live and is why the call is served rather than stubbed -- a behaviour that cannot be configured and one that can are different features. The tape files input at the three places it actually arrives, since there is no fork queue, and `EVNTREC`'s six bytes were measured out of the generated code because this compiler pads some structs to four. |
| [phase47.md](phase47.md) | **Resources go far.** A control panel overflowed the pool by 254 bytes, and the fix was structural rather than smaller dialogs: `rs_load` now PREFERS far memory for any caller that opts in, instead of falling back to it when a file will not fit. Four lines -- and then fourteen addresses truncated into sixteen bits, in two flavours, one of which nothing warns about. The fourteenth hung the desktop with an hourglass and no crash, no `BRK` and no refused call, and was found by bisecting disk images; `tools/nearcast.py` exists so that does not happen twice, and its test puts the fault back. Six accessory slots (`NUM_PROCS` 4 to 7, which is TOS's number), three accessories that coexist, the calculator built as both an application and an accessory from one source, and QED launching FROM the desktop rather than replacing it -- because replacing it makes multitasking permanently harder to add. Pool free 3,074 to 8,192 bytes with all three accessories resident. |

| [phase48.md](phase48.md) | **The AUTO folder, and a control panel with things in it.** An ST's control panel is a host, not a dialog, so this builds XCONTROL's shape -- and needed something underneath it first: `Ptermres` that really keeps the program. All or nothing here, the region being the unit, because both allocators are bump allocators and a partial release leaves a hole neither can hand out again; `src/sys/gemdos.h` had said the opposite since phase 42. `\GEM\AUTO\` runs before the accessories, the CPX modules before the panel that hosts them, and the keep mark after all of it. The CPX contract takes **one `uint32_t` per vtable entry** and not the pointer it wants to be: a `saveds` function on this compiler emits its `tcd` before the body reads an argument the caller left in the caller's direct page, so a second argument of any kind -- or a first one that is a pointer -- arrives as garbage with nothing refused. Found by a screenshot. Then settings across a reboot, which did nothing at all for two reasons that both built clean: a shell edit that had never matched the file, and a `char[14]` padded to 16 that put the header at offset 20 in the struct and 18 in the AES -- now checked by the compiler, with a negative array bound. Plus the desktop gaps: `.APP`/`.TOS`/`.TTP`, Show &#124; Print &#124; Cancel on a document, `.PRG` as the installed name -- and `tools/deskref.py`, which had been agreeing with the target only by never being asked. |

| [multitasking.md](multitasking.md) | **The question, before it is answered by whoever is enthusiastic that week.** gem4xe already multitasks -- seven process records, message queues, event blocks, and contexts that park their extent of the one engine stack in far memory and come back to the same addresses. What it cannot do is hold two APPLICATIONS at once, and that is the ALLOCATOR, not the scheduler: bank $00 leaves 14,336 bytes and a second near region has to fit in it beside the desktop and the accessories. XM/GEM measured against FreeMiNT on that basis -- XM/GEM being DRI's own 1987 answer, 66 C files under GPLv2, whose real content is `SW.C`'s 773 lines of swapping applications to expanded memory, which is the same shape as swapping a near region to the 14.9 MB; FreeMiNT being preemption, which fights a shared stack there is no room to duplicate, on a machine with no MMU to make its other argument. And the middle answer neither camp names: two near regions and an allocator that gives back out of order, which is the prerequisite for either. |

| [6502.md](6502.md) | **Prototyped, not started.** What Calypsi's 6502 banking actually does to a cross-bank call, asked of the toolchain rather than read out of its manual: a plain `jsr` at the slot address, no trampoline -- and the same plain `jsr` from Calypsi's OWN cx16-banked map, so nothing is being missed. Worse, two functions in different banks can share one runtime address and the linker exits 0 with no diagnostic, so a wrong cross-bank call is not a diagnosable error but a confident wrong answer. What that costs the design, the measured 1.48x the 6502 charges for the same C, and the `$4000-$7FFF` contention every other decision waits on. `tools/bsp6502/probe.py` asserts all three. |

| [far-trees.md](far-trees.md) | **All three steps built: every tree a FAR pointer, and since 2026-09-19 `rs_load` PREFERS far memory for any caller that opts in -- whatever the file's size, rather than only when the pool will not hold it. The pool is the exception now: a small-data caller, and a colour-icon resource; one that will not fit and cannot be held far is refused (test-m33, 42 KB and 702 objects, loaded and refused from one source).** Object trees in far memory. The AES used to address every tree with a bank-$00 pointer and load every resource into a 14 KB pool; QED's resource is 34 KB with 682 objects, and where bank $00 had 1,794 bytes free the pool now has **8,192** with the desktop and all three accessories resident (`tools/memreport.py`) and **11,928** measured live with the desktop alone (`test-m17`). The design is ONE path -- every tree is a FAR pointer and a bank-$00 tree is a far pointer whose bank is zero -- so the desktop, GACS and RetroWP are served unchanged by the code that serves a far one. Measured: +26% on the object walk, 0 on the pixels. Who may receive a far address is decided by the application, because the AES cannot tell a small-data program from a large one and a truncated pointer is silent. Order of work, the compiler bugs it walks into, and the oracle already in place: forty gates that draw trees. |
